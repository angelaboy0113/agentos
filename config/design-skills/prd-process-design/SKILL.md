# 基于现有流程写 PRD

先理解系统目前怎么做，再提出改法。与产品经理评审时，每项关键变化应能回答「现在怎么走」「这次改哪一步」「哪些旧行为还沿用」「其他环节会发生什么」。

## 查现状

- 从用户、业务对象、涉及环境和入口出发。用户未指定环境且项目已有默认环境时沿用该默认。只读查授权资料，按项目当前环境核对对应源码分支、业务文档、页面和可取得的记录。记录固定源码证据与生产现场证据各自支持什么。
- 逐个理解独立模块的入口、触发者、输入、校验、输出和状态。沿真实依赖往上下游追，找到谁生成单据、账或状态，谁消费，在哪一步确认成功或处理异常。查清实际顺序后再串流程，用一笔代表性业务对象贯穿。单纯找到菜单、字段或类名只能证明存在。
- 对有状态或金额的流程，按实际适用链路追溯额度或预算来源、占用时点和维度、提交和审批/复核、上账或实际消耗、退回/撤回/关闭后的释放或结转。区分申请、审核、待上账、实上账、待抵扣及剩余额度；这些可能来自不同账或业务对象。查到无某一环节时记录依据。发现延迟、失败、部分成功、重复、存量、跨期等确实有影响时，一并核对。
- 对跨系统变更，核对数据由谁生产、按什么业务对象关联、何时交接、接收方怎样判断成功，以及缺值或失败时由谁处理。只有页面改动时，验证同一页面与相邻动作即可，按实际影响缩小范围。
- 没有证据就标未知，优先补查最接近的已有只读入口。无法从系统回答、且会改变范围或行为的决定，带上现状和选项请用户确认；沿用原卡输入框，避免重问已知口径。参考稿中的案例、金额和规则只对其对应需求有效。

## 设计改造

- 按「现状 → 拟改 → 沿用 → 影响点」组织每个相关模块。优先复用已验证的审批、计量、上账、权限或组件；明确新分支从哪里切入、在哪汇回旧流程。声称「沿用原逻辑」时，简述沿用的触发点、状态和业务结果。
- 对每个关键分支写清业务条件、处理动作、结果与下一责任方。适用时给出推荐的少改方案和必要取舍。把代码、路由、库表定位留在调查证据里，评审稿使用业务术语。
- 金额或状态复杂时用一条完整单据和一个异常场景演算，核对前后状态、余额和处理顺序。比如负数待抵扣 500、可用额度 300 时，说明此次抵扣、剩余待抵扣、后续额度何时可用，以及释放或关闭是否有独立条件。数值只作演示，具体口径以当前任务证据和确认结果为准。
- 把用户已确定的要求、查到的现状和你的建议分开。需要用户决定的规则未确认时，保留调查结果和选项。不要以其他需求的方案补写成本需求事实。
- 从现状链路反推会改变结果的决策，定稿前逐项检查：业务范围与期间归属；触发时点、默认值、日历例外和同批顺序；角色、权限、界面状态及下一步；必填材料、导入校验、重复及更正规则；异常、部分成功、结转和不可用操作。只展开适用项。涉及周期变更时，分别核对业绩来源期间、额度归属、扣减期间和跨期使用，避免把一个期间规则套给所有账。
- 遇到自动任务，至少走一遍空配置、边界日和多条同批；遇到导入或上传，至少走一遍有效、无效、重复与后续可做的操作；遇到绕过原审核节点，说明业务动作是否省略、系统状态怎么记、谁能看到或执行下一步。只写「按配置」、「沿用现有」或「无效时提示」时，继续检查是否已经说清具体触发点、字段、条件和结果。
- 无法从原话、已确认材料或当前系统定论的关键规则，在原卡一次列出彼此独立的待确认点，给出可选行为和受影响结果，收到答复后核对有无冲突。对参考稿与已有答复冲突的规则，向用户指出冲突后再采用。定稿前以评审者视角逐项核查正文的规则是否可读、可执行，并与算例、图和原型一致。

## 随需求选表达方式

- 用用户或系统规定的章节作为外框。可在相关章节加入小节、流程图、表格、例子和原型，按理解难度选择，不要求每份文档出现同样的内容。
- 多角色或跨系统交接适合泳道图。状态多时用状态流转图或表。金额、排序、导入字段和错误提示适合对照表与演算。纯文案或简单字段变更用短文和必要的页面标注即可。
- 流程图应显示关键触发、分支和汇合，图旁保留可读规则。优先选择交付平台支持且能回读验证的图形格式。页面原型按本项目规则以相关真实页面为依据；业务流程图与页面原型各自服务于对应章节。
- 定稿使用大白话开篇，写清业务目标、改造范围及已确认口径。图、表和例子放在解释对应规则的位置。交付前用代表性单据走一遍，确认旧流程接续、新旧分流、关键金额或状态与正文一致；局部变更检查相邻动作即可。确认不足的关键设计回到卡片补齐。
