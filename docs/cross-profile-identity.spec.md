# 跨机器人真人身份与按钮权限

2026-09-06：负责人发起的任务转开发后，originProfile仍为负责人应用。不同应用下同一真人open_id不同；原发起人检查限定同profile，开发管理员表又缺失，导致刷新被误拒绝。

## 实现与验收边界

- `projects.local.json.humanIdentities`用本地稳定真人键映射各profile的open_id。只接受可信本机配置；禁止按姓名、AI判断或回调自报管理员身份连通权限。加载时拒绝重复/歧义映射，配置保存保留该字段。
- `authorization.js`统一判断发起人，同应用仍精确匹配，跨应用仅接受已验证映射；自然语言补充/取消、卡片刷新/停止/补充、详情翻页复用。不能拿别的项目/群的任务操作；原群/消息/应用/执行版本约束保留。
- 只读刷新/翻页允许发起人或该应用管理员，绝不派发AI、审批或停止。普通成员只能创建和继续 `analysis` 只读排查；实施、规划、测试、审计、部署等可执行任务只能由该应用显式配置的管理员创建或继续。停止仍允许原发起人或管理员执行，因为它只收缩执行范围。humanIdentities本身不授予管理员或代码修改权限。
- 本机Leader五应用身份通过各应用读取同一条原始用户消息验证：消息ID、所属群、真人类型、租户一致，负责人侧ID匹配已知发起人/管理员。仅提取发送者ID，不持久化消息正文；补齐五应用管理员与同一真人映射。不更改应用scope。
- 新任务和历史Job都根据映射解释身份，不重写Job发起人、不重放失败按钮。服务空闲后重启生效。其他部署需自行核验映射，无法读取原消息时由管理员通过各应用可信身份查询/定向消息核对，不猜ID。
- 模型核验与权限修复分开：聊天记录实测gpt-5.6-sol；当前用户config.toml默认同名、effort=high，聊天turn显式effort=low，执行任务不覆盖model。客户端某个对话的模型选择不等于服务配置。本次不更换模型。
