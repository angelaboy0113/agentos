# 飞书群 PRD 需求工作台

## 使用

在启用的群中 @对应系统助手说「我要做 PRD」，可以在同一条消息写上需求。单独发入口命令先建立需求卡，再由发起人在同一话题补充目标和材料。普通文字回复无需再次 @。发送截图时建议 @ 原助手以使用现有附件下载流程。多个助手接收同一根消息时，由先取得需求归属的助手接续。其它成员可直接编辑已经共享的评审稿。

Assistant 使用现有只读调查能力，按需核对本系统固定源码与授权入口；相关系统沿已有跨系统授权读取，未登记的对方源码或网页标明待确认。已确认规则、建议和技术证据分别记录。本阶段输出评审稿，既有业务写权限、应用发布和正式审批均与 PRD 隔离。

确定本轮范围后，发起人在原话题发「导出飞书文档」。Runner 复用同一任务和原生 Codex 调查线程，生成具有标题、强调文字和表格的 Markdown，以及原生图片工具生成的 PNG。原型生成沿用任务隔离原生工具，主需求会话保留。结果核验后，以已核实的授权用户身份建立飞书新版文档，回读标题、原生表格和图片，给这一个群授予编辑并回读权限，然后在原需求卡更新链接。文档是评审稿，不会自动覆盖群成员的人工编辑；更新需求后可重新导出一个单独版本。正式同版审批、只读快照与结构化差异合并属于后续。

## 配置

现有实例 data 目录的同级目录放私有 `prd-workspace.local.json`，参考 `config/prd-workspace.example.json`。chatIds 只列获准启用的群。文档发布 profile 需配置用户 OAuth，并由维护者登记该 profile 下准确的用户 open_id 和允许共享的群。OAuth 由飞书 CLI 持有，配置不包含令牌。缺用户授权时，仍可继续分析并保留已核验文件。授权后按原题再次发送「导出飞书文档」即可尝试续投。超时导致创建、插入或分享结果未知时保留阶段，维护者核对回执后接续，避免重复创建。

新任务使用本实例现有 `native-tools-v1`。同一需求跨补充保留原任务、问题和工作区检查点；Codex 读工具仍核对原项目、环境、群和身份。不同需求分别拥有自己的线程。普通任务沿原流程运行。

## 验收与回退

检查同话题无二次 @ 的正文补充、多助手同事件去重、其它成员不能冒用发起人的发布命令。真实交付需回读用户身份、原生样式和表格、图片、群协作者编辑权限及卡片链接。回退先等待空闲，保留正在进行的 PRD 任务、文档链接和投递阶段记录，再关闭 pilot 配置并按原部署守卫回退代码。
