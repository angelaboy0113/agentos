# 使用飞书话题群

话题群让每个提问成为一个可独立查看的讨论入口。AgentOS 的负责人、PM、开发、测试、审计分工、源码同步、管理员权限和生产查询审批保持原样。同群 Codex 受理会话仍共享，后台 Job 独立排队；话题展示不意味着多个任务已经并行执行。

## 创建和接入

1. 用飞书客户端或官方 CLI 创建私有话题群，CLI 显式使用 `--chat-mode topic`。`chat_mode=topic` 与普通群的 `group_message_type=thread` 是两种配置，不能混称。
2. 加入当前用户、原成员和原机器人；继续使用现有应用、profile 和 Secret。换群本身不要求重新登录五个机器人。创建群和添加成员可能需要操作者的飞书权限。
3. 用户建群需要 `im:chat:create_by_user`，成员添加需要对应成员权限。如果用户建群授权还在企业审核，可在原机器人已有建群权限的前提下，由机器人建群并指定真人群主，再由已授权用户加入其他机器人和成员。机器人不应在建群请求里直接邀请其他应用；每批机器人上限 5 个。必须检查失败/待审批列表并回读最终成员，不能把部分加入当作全部成功。
4. 在 `config/conversation.local.json` 开启 `questionCards=true`，保证任务跨角色仍更新原问题卡；本部署同时保持 `groupSessions=true`。旧兼容分卡模式不承诺跨角色进度集中于同一话题。
5. 在 `config/projects.local.json` 把新群映射到原项目，加入 `topicChatIds`。如果旧群停止接单，将旧群从 `chatProjectMap` 移除并加入 `retiredChatIds`。

```json
{
  "chatProjectMap": { "oc_NEW_GROUP": "your_project" },
  "topicChatIds": ["oc_NEW_GROUP"],
  "retiredChatIds": ["oc_OLD_GROUP"]
}
```

这是需要合并到原配置的片段，不要覆盖整份配置。保留 projects、ownerOpenIdsByProfile、humanIdentities、verifyCommands 和源码分支等字段。两个列表必须为字符串数组且不能重叠；缺省不改变旧行为。

修改前备份原 local 配置和状态，保存 SHA-256；确认没有在途任务后停稳旧实例，更新配置并启动同一实例。不创建第二套消息消费者，不删除旧群或旧运行数据。

## 提问和回复

- 在新群点击“新建话题”，@ 项目负责人描述一个问题。
- 发起人或管理员在该话题内回复原提问、主卡片或已关联消息，继续同一问题。独立问题另建话题；其他成员跟帖仍按现有发起人和权限规则处理，不能控制他人的任务。
- 主卡片使用原消息回复接口，显式 `reply_in_thread=true`；进度、结果和最终 @ 提醒沿用原话题。原有卡片翻页及审批继续使用同一主卡片。
- 整条任务链结束才 @ 原发起人；待生产查询审批时单独 @ 指定环境负责人。消息可能受飞书投递、可见范围及客户端展示影响，首次接入需真实群验收。
- 群内内容仍对群成员可见，话题不是私密工单。不同话题的视觉隔离不改变群共享原生会话模式和每轮权限检查。

`retiredChatIds` 中的群在 AI 受理前被忽略，旧卡片不再允许继续执行、批准或补充任务；历史结果翻页和刷新保留。不自动撤回旧消息或移除成员，不给旧群发送额外迁移消息。

## 历史与记忆

旧群聊天、Job、Mission 和卡片保留原 ID 及归属；不会伪造为新群消息，也不会自动重放。原生 Codex 会话按群、机器人、角色和项目隔离，所以新群建立新群会话，不自动复制旧群上下文。团队规范、项目源码和环境配置继续复用。需要迁移旧群会话时，应另行明确范围、核验成员可见性并备份，不能直接改历史消息的群 ID。

接入时回读 `chat_mode=topic`，核对真人及应用成员集合，逐一用五个机器人读取群信息。启动后检查 health、唯一运行实例、消息和卡片消费者。最后由真实用户在新话题 @ 负责人问候，再验证跟帖、任务进度和最终提醒的位置。

实现：`config.js`、`server.js`、`conversations.js`、`questions.js`、`live-cards.js`、`card-actions.js` 和两个飞书发送适配器。流程总图的角色与审批链没有变化，话题是该流程的消息展示入口。
