# 持续并发执行验证

版本：v1.5.1
日期：2026-09-22

## 验证对象

本次验证覆盖新建只读分析的三项变化：一张问题卡只保留一个持久 Job；源码、数据库和网页工具结果回到同一个 Codex thread；单机默认以 3 个 Runner 槽执行不同卡片。

实现边界保持不变：修改代码、数据、配置、部署或业务状态仍走原交付链与权限门。旧 `analysis_review` 任务保留旧结构，不迁移、不重跑。

## 自动化结果

- `npm test`：320/320 通过。
- `npm run check`：320/320 通过（包含语法检查与完整测试）。
- 新回归验证源码 → 环境工具 → 源码综合只使用一个 Job ID，完成后没有 `nextJobId`。
- 新回归验证首次入口已经带数据库查询时执行环境工具 → 原开发会话综合，仍只使用一个 Job ID；新任务不会再进入旧式多 Job 接力链。
- 原因调查允许用数据库异常、源码调用链、同批次对照和状态轨迹等独立证据形成分级结论，不再把下游原始错误响应设为唯一完成条件。
- 新回归验证环境工具先执行时仍把已明确的 UAT/PRD 传入后续源码分析，避免再次询问用户已经给出的环境。
- 新回归验证 MySQL 查询可用全参数绑定的 `contains` 和 `in` 精确查日志参数或候选编号；schema 可按最多20个候选字段做精确发现，仍不接受任意SQL、联表、写操作或模型提供函数。
- 新回归验证只读调查收到模型容量不足时保留 thread 并自动接续一次；实施任务不自动重放。第二次失败保留明确 `MODEL_CAPACITY` 诊断，卡片不再显示原因未知的 `EXECUTION_ERROR`。
- 新回归同时启动 3 个 Runner 槽并观察到峰值并发 3；配置低于 1 或高于 8 会拒绝启动。
- 新回归验证问题卡从用户原始提问开始累计“总耗时”，跨后续源码、网页和数据库 Job 仍使用同一时间起点；环境排查每 10 秒发送进度心跳，促使执行中卡片持续更新。
- 新回归验证已登录业务网页的单次快照超过工具预算时，本机自动压缩可见文本、选项和控件清单，保留可用页面引用并标记截断，由同一排查会话继续执行，不再以 `RESULT_LIMIT` 终止整项问题。
- 新回归验证环境证据必须匹配当前租约、environmentId、queryId、scopeHash、读取时间、行数和结果哈希，随后写入同一 Job 上下文。
- 新回归验证核心目标与截图旁支目标分开：核心目标全部核实即可完成，可选旁支不会使卡片变红。
- 新回归验证连续 Job 能识别上下文中的同一网站零记录结果，阻止改写查询目的后的第二轮空转，并允许改走数据库或源码证据。
- 新回归验证数据库查询返回的脱敏关键记录被结构化保存，最终综合即使省略它们，卡片摘要与详情也会补回最多 5 条直接证据。
- 既有回归继续覆盖登录等待/自动恢复、共享 Chrome 的每 Job 标签隔离与授权复核、取消租约隔离、旧工作流兼容、卡片终态和完整消息投递。

受限沙箱内需要监听临时 `127.0.0.1` 端口的用例可能收到 `EPERM`。在允许回环监听的发布检查环境中重跑后 317 项全部通过；这不是产品逻辑失败。
