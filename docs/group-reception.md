# 群接待、共享公开状态与故障接续

适用 AgentOS 1.77.0，2026-11-08。Node 与依赖兼容条件沿用 package.json；无新增依赖。功能默认关闭，业务任务、源码分支和数据授权不因接待而改变。

## 配置与入口

复制 config/reception.example.json 为部署私有的 config/reception.local.json（或 AGENTOS_RECEPTION_FILE）。填写本部署已登记的 profile、绑定群 chatIds、projects 中 humanIdentities 的 humanId。每个 profile 对应的 open_id 必须同时是该应用的可信管理员；缺失时启动拒绝。since 是本次启用时间，用于防止历史失败卡批量重开；示例日期必须改为实际启用时间。配置变更需在无活动任务和待投递时重启唯一实例。

复用各机器人的单聊接收、读取群消息和发送消息权限，不借用个人身份；读取群成员名字另沿用 reply-addressing 配置。群全消息权限本身覆盖机器人所在群，程序仅接收配置绑定群；原生事件入口和控制面均验证身份、群与原话题。新增配置必须加入私有迁移备份，不放入代码包或 Git。未收到事件时先核对应用权限/订阅、入群身份、当前消费者 ready，不能因控制面模拟通过就认定平台入站正常。

管理员私聊任意已启用助手，例如：“我今天暂时不方便回复，可以公开说我在出差，到今晚20点失效。”系统保存公开短说明、是否方便回复、带时区的失效时间及来源审计，四个助手读取同一状态。信息不明确时先询问，不猜行程；可以说“我回来了”恢复接待。只共享获准公开的短说明，不共享私聊正文或凭据；过期立即停止对外引用。单聊非管理员不能设置，不创建业务卡。

## 对话与提醒

- 明确 @ 助手的纯玩笑/夸奖：原话题只回复最终短文本，不展示思考、工具或任务卡，不追加完成通知或成功表情。包含真实业务需求、附件、查数、权限申请时仍走正式业务流程。
- 同一已绑定公开任务话题中，用户实际 @ 管理员求助：从接收时间起等待 helpDelayMs（默认三分钟）。管理员先回复、问题已解决、关闭或进入新一轮时取消。只由原问题的 profile 接话，同类求助合并，reminderCooldownMs 控制接待消息冷却，不限制业务任务执行。
- 没 @ 助手但明显追加业务需求：偶尔提醒 @ 本话题助手，不能执行这句业务请求。普通讨论、收到、我看看以及其它话题保持安静。已有卡片话题不匹配时不以“最近任务”猜归属。
- 模型接待分类只允许 reply/none；即使输出了开任务/环境访问要求，程序也拒绝执行。用原有称呼配置处理名字与例外，不判断性别。

接待消息采用少量不同语句和确定性选择；失败重试冻结同一内容和幂等键，不因重启换文案重复发送。平台幂等窗口将过期而回执不确定时转人工对账，避免重复消息，不截停业务任务。

## 失败监控与真实恢复边界

任务状态事务原子记录故障事件，另有两秒轻量投影轮询补漏、处理持久队列。只处理 since 之后当前原话题、当前 generation、最新任务的失败；私有任务、已关闭卡、被后继替代的任务和旧失败不自动恢复。

已知启动前 account/read、initialize 超时可在固定源码、原身份和规范指纹核验通过后重新排队同一任务；保留原失败结果和审计。不把 turn/start、模型执行、数据库超时、业务写入或未知错误一起重放。网站登录/模型容量等待继续由已有专用检查点处理器接管。附件失败复用原文件投递箱，不重新查询。核验未通过或权限/未知程序错误登记为待维护，保留真实缺口，不伪称自动修复，更不会自动提交/发布任意代码。

原卡显示当前已核实的接续状态，恢复完成后正常结果替换诊断；颜色仍由真实业务结果及交付验收决定。已有失败与超时管理员通知继续使用原机制，接待服务不再次无条件 @ 管理员。耗时本身不是停止理由；没有新增整任务时间、轮次或调用次数截止。

## 持久化、验收与回退

ownerPresence 保存共享公开状态；receptionInbox 保存分类、三分钟等待与发送回执；recoveryEvents 保存诊断/接续审计。全部使用控制面 JsonStore 同一事务，勿在运行时用独立脚本覆盖 agentos.json。重启恢复队列，重投同一消息；业务任务租约、固定源码和文件收据沿用原机制。

运行 npm run check 和 node scripts/verify-capability-package.mjs。回归涵盖多 profile/话题、管理员/非管理员、等待取消、并发、重启幂等、错误分类、文件投递顺序与原卡状态。真实 API 验证与合成入站必须分别报告；测试用临时消息需记录 ID 并撤回，不能删用户消息。检查 /health 的 receptionProtocol、receptionBusy 和各消费者日志；上线不得另启第二套消费者。

关闭开关可停用新接待，等待自然空闲后重启；保留状态与收据防止重新启用后重复投递。回退旧代码前先停止唯一实例并备份运行态，保留新增字段；用已验证旧提交和原配置启动，不倒灌整个旧 agentos.json 覆盖上线后新任务。macOS 本机代码包提取及原生 Feishu API 已测；Windows/跨机全私有迁移和真实用户自然入站须另行验收。
