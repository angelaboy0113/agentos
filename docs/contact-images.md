# 按姓名或工号查询联系人并回复信息图

## 用途与当前边界

在已配置的飞书群 @机器人，输入姓名或完整工号。主对话模型选择 `lookup_contact` 动作，程序按机器人自己的通讯录权限读取资料：唯一匹配则生成 PNG 并回复原消息/原话题，重名则先列候选。它不是飞书客户端截图，不操作鼠标键盘，不启动或切换你的飞书/Chrome窗口，不使用部署者个人 user token。绘图使用独立的无头 Chromium，串行渲染、阻断页面网络与脚本；仍会占用一定CPU和内存，不能承诺计算资源零影响。

这次接通的是联系人信息图，不等于已经支持任意流程图、任意文件或原生个人名片投递。头像位置使用姓名首字，未下载真实头像。岗位、上级和入职日期仅在接口原本获准返回时展示，不为了凑齐图片扩大权限。手机号仅显示脱敏值，不申请手机明文权限，不展示个人邮箱。

## 安装与配置

沿用 `package.json` 的 Node >=22.13且<23、`npm ci` 和 Playwright Chromium依赖；目标机器执行 `npx playwright install chromium`。Windows使用相同Node代码，不启动桌面自动化，需在Windows实机验收中文字体、无头浏览器与文件权限；不能以macOS渲染替代Windows验收。

在程序目录复制 `config/contacts.example.json` 为 `config/contacts.local.json`（已有文件先备份，勿覆盖）：

```json
{
  "enabled": true,
  "indexFreshnessMs": 900000,
  "scopes": [{
    "projectId": "your-project",
    "chatIds": ["oc_YOUR_GROUP"],
    "profiles": ["your-owner-profile"]
  }]
}
```

- 项目、群和profile必须对应真实项目绑定；不因机器人在群里就自动启用。可选 `senderIds` 为该profile下获准提问者的open_id数组；省略表示配置群内的成员可发起。私聊当前不开放。
- 默认配置文件是 `config/contacts.local.json`，可用 `AGENTOS_CONTACTS_FILE` 指定。每次请求及发送前重读配置；新增程序/提示词需要在任务和对话空闲时受控重启。
- 可选 `workEmailDomains` 为该共享范围允许展示的工作邮箱域名，例如 `["company.example"]`。API的`enterprise_email`是飞书邮箱服务字段，需另有受雇信息等权限且企业启用飞书邮箱；本功能不额外申请这些宽权限。普通`email`仅在域名精确匹配时作为工作邮箱展示，未配置则不回退，个人邮箱不展示。
- 查询和投递始终用提问所@的同一个机器人profile；不切换其他机器人或个人账号补权限。不同profile的open_id不能互换。

## 飞书应用权限需要真人批准

负责人应用的开发者后台 → 开发配置 → 权限管理：申请需要的应用身份只读权限，至少保证能读姓名和工号；部门、企业邮箱按需启用。

| 权限 | 用途 |
| --- | --- |
| `contact:contact.base:readonly` | 基础通讯录访问；仅有它不代表姓名/工号字段均可返回 |
| `contact:user.base:readonly` | 成员基本信息，如姓名 |
| `contact:user.employee_number:read` | 精确核对工号，保留前导零 |
| `contact:user.department:readonly` | 组织归属；部门名称接口也须有相应读取能力 |
| `contact:department.base:readonly` | 按授权部门遍历和取得部门名称；具体是否需要以后台对应接口要求为准 |
| `contact:user.email:readonly` | 邮箱字段；只有匹配配置中workEmailDomains的公司域名才作为工作邮箱展示 |
| `im:resource` 与机器人回复消息权限 | 上传PNG、回复原消息；已有消息权限不代表新应用也有 |

同时配置**通讯录数据权限范围**，包含确实需要查询的人员或部门；接口权限和数据范围是两件事。不擅自选择全公司，不改变应用可用范围。创建版本并提交企业管理员审核/发布，再只读核实字段返回。官方权限申请API只能申请应用已经配置、待授权的权限，不能代替开发者后台新增字段或指定数据范围；没有待审字段时不能声称申请已提交。

官方规范：[用户信息](https://open.feishu.cn/document/server-docs/contact-v3/user/get)、[通讯录授权范围](https://open.feishu.cn/document/server-docs/contact-v3/scope/list)、[申请与发布](https://open.feishu.cn/document/server-docs/application-scope/introduction)。

## 实际链路

1. Codex提取姓名/工号字符串；工号 `00110036` 不转换为数字，不当作open_id。
2. 程序先核对项目、群、profile、可选senderIds；再读取该机器人获准的通讯录范围。
3. 分页读取范围内的明确人员和部门成员，按姓名包含匹配、工号完整相等匹配；不提前把第一页当全量，分页失败不确认唯一性。全员范围同时返回用户组时，先由飞书校验根部门0可读，再完整遍历根部门及所有子部门，无需额外申请用户组读取权限。若仅有用户组且无法核实全员根部门，则明确说明不能确认完整范围。较大范围首次查询可能较慢，目录候选保存在本机SQLite索引；人员读取最多4个请求并发，分页完整性不变，不设置查询任务总时间上限。
4. 重名返回姓名、部门和工号候选，不自动选第一人；用户在同一问题中选择后，重新查询当前资料。候选不跨提问者、项目、群或机器人使用。
5. 只将允许展示的字段交给本机离线HTML模板，手机号脱敏，缺失字段显示“未提供 / 无读取权限”；生成PNG。完整通讯录资料不交给模型，候选确认仅提供必要字段。
6. 图片绑定原提问者、原消息、问题、项目、群及profile，保存SHA-256、大小和生成回执。发送前再次核对配置、人员可读性、可见字段和图片摘要；变化时不发送旧图，提示重新查询。
7. 用原机器人回复原话题。投递失败保留输出、幂等重试，不再次调用模型或全量找人。当前只回原话题，不私信被查询的人。

## 目录索引与实时复核

位置：`<AGENTOS_DATA_DIR>/contact-index/directory.sqlite`。索引按机器人profile、当前通讯录范围和权限指纹隔离，与团队知识库是两个不同的SQLite文件。

完整目录读取后，仅把姓名、工号、open_id、部门ID和离职标记存入本机SQLite，不保存手机号、邮箱、头像或完整人员正文。默认15分钟复用（indexFreshnessMs=900000，0关闭复用）；这只是索引有效期，不是任务执行时限。每次查询仍重新读取应用数据范围和权限状态，指纹变化不用旧索引；目标人员资料及可见字段实时读取，重名候选逐一实时复核，发送前再校验。索引未命中时重新完整读取，以便找新成员；多个同时触发的相同范围目录读取合并。首次建立索引仍可能较慢，后续不必每次遍历全公司。

索引是一次多页读取的结果，并非事务快照或实时组织事件同步。窗口内新增的同名人员可能尚未出现，图片明确标注目录索引生成时间与本次人员查询时间；需最严格实时目录核对时将indexFreshnessMs设为0。不把索引时间冒充所有人员同时核实的时间。

## 保存在哪里

`<AGENTOS_DATA_DIR>/contact-images/<绑定摘要>.png` 和同名`.png.json`保存信息图与生成回执；`data/agentos.json`的对话`outcome.contactImage`保存范围/校验引用，`contactImageMessageId`保存发送结果。CLI上传副本在`data/lark-cli/images/`。它们含人员信息，应使用本机受限权限、纳入停机备份，不提交Git、不进入团队共享知识。没有自动图片清理服务；确认投递结束后按团队保留策略人工归档，不删除等待重试的文件。

## 你怎么测试

权限发布并部署后，在已启用群按顺序发：

1. `@项目负责人 工号00110036是谁？给我一张他的联系人信息图。`
   预期：姓名与工号都能核对时，图片回复本话题；保留00110036前导零。无字段权限或范围不含此人时明确说明，不编造图片。
2. `@项目负责人 查一下张三的飞书资料，整理成图片给我。`
   预期：唯一人员出图；重名则列候选。回复该问题中的候选序号，例如“第2位”，再确认生成图。
3. 用另一位同事、另一种工号重复，核对图片不会串人、串话题；陌生工号应说明“当前获准范围内未找到”，不等同于公司无人。
4. 在测试配置验证关闭功能、撤销成员范围、资料变化时不继续投递旧图片；不要拿真实群撤权演练影响他人。
5. 查询期间正常操作你的开发机：窗口、焦点和鼠标不应被AgentOS切换。后台绘图有计算资源消耗。

维护者检查/admin任务记录中的原对话：决策是lookup_contact，未创建源码Job；outcome存在图片登记和投递messageId。发送失败看deliveryFailures/deliveryError和文件摘要；查询失败看权限、范围、字段、分页或后台Chromium依赖，不通过换个人账号解决。

## 验证等级

代码回归使用合成人员验证前导零、重名、候选作用域、字段缺失、配置撤销、图片篡改、可见字段变化和失败重试。macOS已实际渲染合成中文PNG。真实接口只读检查可证明当前授权及字段是否返回；不能把它说成全公司查人、真实群图片投递或Windows实机验收已通过。

本机只读权限自查（只输出权限名、第一页范围数量与字段是否存在，不输出人员ID、姓名或原始响应，也不改权限/发消息）：

```sh
node scripts/check-contact-access.mjs --profile your-owner-profile
```

## 岗位与完整部门路径

岗位只使用飞书标准job_title字段；该字段需要`contact:user.employee:readonly`（用户受雇信息）只读权限，没有更窄的单独岗位权限。接口可能同时返回员工类型、入职日期和自定义受雇字段，但程序仍只提取图片既有白名单字段，不保存完整人员正文。不要把员工类型当岗位，不从姓名或工号猜测。

完整部门路径通过部门接口的parent_department_id逐级拼接，需要`contact:department.organize:readonly`。采用机器人身份，不能改用只支持user token的department_path字段借用部署者可见性。根部门名称仅在飞书实际返回时加入，多个任职部门分行；父级权限不足、父链缺失或循环时标注“上级路径未核实”，不会把末级名冒充完整路径。发送前重新核对岗位、路径和上级，变化后不发送旧图。旧版图片仍保留在本地，新的查询生成新格式。

新增权限须企业管理员批准并发布；沿用已批准数据范围，不自动扩大人员范围或申请手机号明文。权限未生效时岗位仍会显示未提供，路径会明确标注缺口。新代码须在任务/对话空闲时备份重启，权限生效后下一次读取即可使用，索引授权指纹会相应失效并重建。
