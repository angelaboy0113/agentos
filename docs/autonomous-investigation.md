# 原问题自动自查与续查

## 使用方式
群内一次提问后，已有权限内的只读调查自动继续，不需要每轮回复“继续”。新分析使用一个持续开发 Job；结果仍为 `partial + continue` 且没有外部阻碍时，本轮结果写回原 Job，并恢复同一个 Codex thread 自动补查。环境查询仍经现有目录、范围和审批门控；登录仍在运行 AgentOS 的电脑上完成，不自动批准、不扩大权限、不变更业务数据。

## 完成与暂停
源码分析输出 investigation：status 为 complete/continue/wait，goals 为稳定 id、verified/open、evidence，attempts 为实际尝试，nextStep 为下一步，blocker 为外部阻碍或 null。新调查以 `original-question` 作为唯一必需目标，覆盖原问题的所有问句；调查中发现的字段、网页日志等只作为可选线索。程序将新增线索降为可选，原问题验收项及证据通过后才允许绿色完成；原问题仍未核实时继续调查或保留部分结果。必需的源码版本、真实工件与交接校验仍生效。升级前已在途、尚未产生 `original-question` 的旧任务沿用旧目标校验，历史终态卡片不会自动改色或重跑。

有证据推进就继续。同一环境已经调查两轮后，如果新证据给出了业务主键或更小范围，可以把补查绑定到仍未完成的核心目标再执行一次；目标和证据摘要均未变化时，改写查询目的不会绕过收敛检查。同一 Job 的源码自查最多自动增加两轮，相同目标证据重复一次即停止空转。用户明确要求深度/彻底排查时，查询命中条件和中间状态不能替代上游形成原因；仍写“为何形成尚未核实”的因果线索会重新打开核心目标。等待外部配合必须声明具体登录、授权、必要输入或工具不可用，提供已尝试路径、阻碍证据和所需动作。卡片保持未完成，不能为了绿色虚构结论。结构检查不能证明模型所写证据在语义上真实，仍可能误判工具是否可用；这不是复杂问题必然解决的承诺。

## 实现与部署
config/task-result.schema.json 提供可空 investigation，并允许环境查询用 goalIds 声明定向补齐的核心目标。源码执行器自查完成条件；store 原子保存 partial 续查上下文，Runner 通过 `continuous-analysis-continue` 在原租约和原 Codex thread 内继续，不派生新 Job。实施类任务不适用。缺少清单的旧结果不能在新版源码执行器获得绿色完成。

更新程序和 schema 后空闲重启，无新增私有配置。已经结束的历史问题不会自动重跑，须在原话题重新要求继续。原生 Codex 和 AgentOS 的工具可用性仍不同，本变更解决续查调度和自查机制，不声称能力完全相同。

## 验证
回归包含完整目标、遗漏目标、旧缺口关闭、无新增证据暂停、新证据继续、明确登录阻碍、同问题原子续查、身份保留、不携带环境授权、重复事件拒绝和真实本地 HTTP 事件路由。使用模拟证据，未查询真实数据库或向业务群发送测试消息。Mac 运行实例部署；Windows 未实机验证。
