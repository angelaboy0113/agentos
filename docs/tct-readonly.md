# Private-cloud TCT read access (1.53.1)

TCT is a separate scheduler provider, even when its executor groups belong to TSF. Do not assume it is XXL-JOB or infer a second login URL for another environment.

A maintainer merges entries from `config/tct.example.json` into the deployment's `environments.local.json`. Replace every example origin, tenant ID, region, project, owner and group ID using the actual console. Store username/password in the existing local credential backend under `credentialRef`; never put them in JSON, model input, Git or logs. Use independent environment entries and exact reviewed `groupIds` for test/production. A shared company login is possible; it does not grant cross-group tool access. Restart the managed instance only after its normal idle/backup checks. The TCT kind is configured by a maintainer, not the automatic MySQL/Nacos enrollment UI.

The current adapter supports the private-cloud subaccount login protocol with RSA-2048 transport encryption and CSRF. It does not execute downloaded client JavaScript. CAPTCHA/MFA or changed encryption protocol requires the maintainer's real login verification; login writes are never blindly retried. Sessions stay in process memory and concurrent tools with the same target/credentials share authentication. After an explicit session/CSRF expiry, a fixed read may authenticate once and retry that same read. A network failure keeps its own diagnostic and does not restart a whole business task. Each network operation has a 20-second timeout (not a total task timeout). Existing task renewal applies. TCT read results, including small responses, are saved as scoped job tool-result references; list_tool_results/read_tool_result recover them after restart or a later environment phase. Group/task locators help select records. Original fetchedAt and completeness remain intact; recovered records are historical evidence, not a fresh platform read. No total tool-call/round/job deadline is added.

The selected environment's tool directory provides `connection`, `groups`, `tasks`, `task_detail`, and `task_batches`. The only API actions are DescribeGroups/DescribeTaskRecords/DescribeTaskDetail/DescribeTaskBatchRecords, version 2018-03-26. Task IDs retain the platform's exact string: decimal IDs preserve integers larger than JavaScript's safe number range, and legacy task- identifiers are also supported. Numeric coercion and arbitrary identifier syntax are rejected. Task membership is checked from the approved group before detail or batch requests; returned group/task ownership is rechecked. Every HTTP request rechecks current authorization. The account can still have broader cloud permissions: program-controlled reads do not prove a cloud-side read-only account.

`tasks` and `task_batches` expose `nextOffset`, total, completeness and read time. Continue until nextOffset is null when a complete list is needed. Empty missing pages fail visibly. Different pages are not a transactional snapshot, and changing totals may require a new verification. Groups without an ID returns the configured scope, explicitly not live metadata; pass a configured group ID to read current metadata. It never returns the tenant-wide inventory. API reads share a per-origin 250 ms pacing queue; an explicit RequestLimitExceeded response backs off 1.5 seconds and retries that read once, then reports the real failure. This is request pacing, not a total task/call limit. Task parameters, code payloads, raw logs, access addresses, session cookies and credentials are excluded. For Java tasks only, a bounded fully qualified class-name TaskContent is exposed as javaHandler, allowing source-to-scheduler mapping. Other payload formats are never exposed; a similar task name alone does not prove it writes the target table. This release does not implement execution-log reading, workflow investigation, task triggering, stop, edit or delete. Request only the supported evidence; do not claim those integrations are available. Scheduler update times are not application deployment times.

Verification: run `node --test test/tct-tools.test.js`, `npm run check`, and `node scripts/verify-capability-package.mjs`. A real deployment must separately verify each environment's connection, group metadata, task pagination and batch response using its actual credential reference. An empty batch list is a successful read, not proof that every task has execution history. Do not send group test messages or run jobs as a connection test.

Code packages must include both TCT modules, policy, example and tests. Private migration uses the existing encrypted configuration/credential workflow; no session export is required. Keep the real group/namespace inventory and connection acceptance in the deployment's private records. Only macOS has been checked against an actual deployment; Windows/Linux credential storage and cross-machine migration require their own acceptance. To roll back, wait idle, back up runtime/configuration, remove only the new TCT environment entries, then deploy the reviewed prior code through the normal maintenance procedure. Never restore an old full task state over newer results.
