# Private remote login verification

Version 1.126.0. A reviewed website entry may opt into `loginNavigation.remoteQr: true` together with `interactive: true` and its exact reviewed login button steps. See `config/remote-login-qr.example.json`. No new Feishu permission is required if that robot can already send private text/images to its trusted administrator.

The normal waiting-login poll renews the original read grant, checks the actual task-owned browser, opens the reviewed interactive login entrance, and captures only one unambiguous visible QR image. It sends the challenge privately through the original robot to the administrator configured in all three trusted bindings (groupOwner, project owner list, environment owner list). No group QR, requester substitution, session copying or cross-system authentication sharing is permitted. Browser sessions remain persistent and scoped to project, tier and origin. An API token does not authenticate a browser.

Delivery generation, hash and receipts are persisted in `remoteLoginQr`; challenge bytes and URLs are excluded from runtime state, model context, business screenshots and group cards. Retries use the same generation/idempotency key. Temporary PNGs and the CLI upload copy are removed after delivery attempts. Existing matching challenges are reused; cancelled/withdrawn tasks are cleaned up. Successful authentication retires the private challenge and the existing login continuation queues the same original job, preserving question owner, source commit, tier, saved evidence and approved read scope. No business operation is replayed.

For a private application whose logged-out fallback looks like a normal page, `loginNavigation.privateEntryMarkers` accepts the exact visible lines verified on that fallback. The browser requires all configured lines and the exact configured login label on the application origin and path. It enters the normal login wait before attempting to read public scripts. Deployments using Shared Chrome route reviewed remote-QR entries through the existing isolated browser so the challenge and resumed read use the same tab.

When a challenge expires, it is withdrawn and not blindly resent. The configured administrator may privately reply `刷新扫码` to that same robot; the program reloads the authorized login page and obtains a fresh challenge. Group and non-owner refresh messages are ignored. Ambiguous/missing QR images, browser automation failures and failed private delivery remain real diagnostics; none is treated as a wrong password or business success. Failed deletion retains its receipt for cleanup retry without blocking successful login recovery. Website/platform verification or first-time authorization still requires the real person.

Checks: regression covers private owner destination, opt-in, identity/tier isolation, concurrent observation, retry/restart idempotency, expiration, terminal cleanup and same-tab QR capture. Actual Feishu/website scan and business completion must be reported separately from synthetic browser checks. Enable/disable private configuration during safe maintenance and preserve pending state and encrypted credentials on rollback.
