# CNB build-history read access (1.99.0)

Use the native build-history provider for CNB deployment investigations. It avoids a browser/CDN/session dependency for this supported evidence. It does not remove the existing controlled browser for other websites, and does not silently copy a person's browser cookies. A Git code-read token, a website session, and an OpenAPI build-history token are separate authentication scopes. Do not tell a user they must log in every fourteen days merely because one browser session expired. Check the actual credential's expiry and the failed authentication path.

## Configure and verify

A maintainer adapts `config/cnb-history.example.json` into the deployment's private environment configuration. Register each project and test/production tier separately, with exact reviewed repository paths and the original owner/profile policy. Repositories must be real configured sources, not inferred from a similar name. The API origin is the official HTTPS `https://api.cnb.cool`. No model-selected URL, host, proxy or method is accepted. This provider currently does not support a self-hosted CNB API.

Create a dedicated access token with **repo-cnb-history:r** and only the required organization/repository resource scope. Leave code writes, build triggers, management, raw logs and other account access unselected. If the operator deliberately authorizes one history-only token for multiple systems, it may be shared as a credential reference; every environment still validates its own exact repositories and every request rechecks that environment grant. The platform token may cover more repositories than the program permits, so record the actual scope honestly rather than claiming it is organization-limited. Save the token as `{username:"cnb", password:<token>}` in the deployment's existing encrypted credential vault under `credentialRef`, using hidden local input, never chat or Git. Set expiry according to the operator's selected policy; a token can still be revoked or invalidated before that date. No credential-creation API, token renewal or browser login is implemented by this provider. An OAuth application with refresh-token support would require separate registration and implementation; do not claim that integration already exists.

Run the controlled `connection` tool for each configured environment and representative repository. It performs an actual one-record history GET, not a configuration-only assertion. Without a repository it checks the first configured repository only; this is not acceptance of every repository. The `build_repositories` tool lists reviewed configuration and explicitly reports `metadataVerified:false`. Record actual token scope, verification time and the tested repositories in private deployment records. Missing token, expired/revoked token (401), permission denial (403), network errors and missing history pages remain distinct. A 403 does not prove a private repository does not exist. Permission changes require the operator's normal approval. Activate configuration/code only through the deployment's idle, backup, stop, start and acceptance procedure; changing configuration invalidates existing plan fingerprints.

## Tools, evidence and recovery

`build_history` uses only **GET /{repo}/-/build/logs**, following the official OpenAPI contract at [api.cnb.cool/swagger.json](https://api.cnb.cool/swagger.json). Inputs are one configured `repository`, positive `page`, `limit` within the configured page size, and optional official filters `createTime`, `endTime`, `event`, `sha`, `sn`, `sourceRef`, `targetRef`, `status`, `title`. Date filters must be valid YYYY-MM-DD dates. `page_size` has CNB's documented maximum of 100; this is pagination, not a total history limit. Follow `nextPage` until null for complete coverage. Keep the same filters and page size. CNB may return total as a decimal string despite the integer OpenAPI declaration; canonical nonnegative strings within the safe integer range are normalized without rounding. When totalCapped is true, the total is only a lower bound: continue beyond it until a short terminal page. Empty missing pages, short nonterminal pages, inconsistent totals, malformed replies and wrong-repository responses fail instead of becoming a false empty result. Results observed across pages are not a transaction snapshot; a changing total may require a fresh verification.

Each network read checks the current authorization. Short-lived 429/502/503/504 responses retry the same GET once after a one-second backoff, rechecking authorization; they do not replay model execution or business operations. Each request uses the configured timeout, with no whole-task, round or call deadline. A single response page has an 8 MiB transport guard; use a smaller limit if needed, without narrowing the overall requested history. Redirects are not followed and bearer credentials never go to another origin. No code evaluates downloaded JavaScript. No raw response bodies, variables, pipeline scripts, raw logs, user details or arbitrary platform links are exposed; output is a projection of build number, exact repository, title, source/target branch, SHA, event, status, start time, duration and sub-pipeline counts. Known token material and credential-shaped text are redacted.

History results include `fetchedAt`, completeness, `nextPage` and a result hash, and are persisted to the existing scoped tool-result store even when small. A later phase can locate and read the original result instead of fetching all history again; a new connection check still verifies current access. Restored evidence keeps its original read time and is not described as current. The model-visible tool directory and execution progress carry this evidence through the existing environment investigator. Generic input errors can be corrected in place, while actual authorization or integrity failures preserve evidence and stop that read.

Build `createTime` is the platform's build **start** time. A successful pipeline plus branch/SHA proves that recorded pipeline result, not that every service is currently on that revision. For an application deployment conclusion, correlate the actual deployment event, application and successful pipeline with the authorized runtime-version or release evidence. Never substitute Git commit time, latest branch tip or build start time for actual deployment completion. If live runtime evidence is unavailable, say exactly which part is verified.

## Acceptance, migration and rollback

Run the isolated test runner for `test/cnb-tools.test.js`, relevant environment/diagnostic tests, the full check, and `scripts/verify-capability-package.mjs`. Tests cover concurrent system/tier scope, fixed GET only, credential removal, full pagination, invalid inputs, scope/response failures, 401/403 separation, short idempotent retries, revocation during retry and persisted evidence across phases. Synthetic tests do not prove the operator's token, CNB availability, live deployment or real Feishu task completion. Verify actual reads separately after secure credential enrollment. No build/deploy should be triggered for a connection test.

Include the policy, adapter, test, example and this document in code packages. Existing encrypted migration rules carry private environment entries and vault data; do not copy session cookies or publicize actual repository inventories. Other operating systems and complete cross-machine restoration require their own acceptance.

For rollback, wait idle, back up current configuration, vault and state, remove only the new CNB-kind environment entries, then deploy the tested prior code through the normal maintenance procedure. Preserve saved result files and current task data. Do not restore an old complete state over newer user results. Existing source Git credentials and browser sessions remain independent.
