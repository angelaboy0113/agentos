# 本机状态请求：性能与超时接续

用于解决 Runner 已交出调查步骤、但本机接口回复暂时丢失或超过单次等待时间的问题。领取任务、环境步骤准备/领取、环境结果回传、源码接续及关键任务事件使用 `durable-control-v1`。业务数据库查询仍按原授权、租约、只读范围和证据验收执行。

## 当前流程

1. 每次关键请求生成一个随机请求编号，绑定接口、内容摘要、Runner 和租约。服务端对并发的同号请求合并处理。
2. 状态变更和回执索引在同一个状态事务中提交。响应正文先原子保存到私有回执文件；索引与正文摘要一起写入状态，未提交的状态变更不作为已受理回执返回。
3. 单次 HTTP 请求仍有10秒等待时间。发生超时或回复丢失时，Runner查询该编号的持久回执：已提交则取回原结果，仍在处理则继续等待；只有新协议确认没有提交时，才使用同一编号和原内容重送。
4. 这不会重新调用业务查询或创建另一轮调查。已保存的环境结果继续回到同一 Job；同一环境领取只记录一次开始事件。执行类回执返回前仍核对当前租约和取消状态，旧租约不能恢复执行。
5. 未提供新协议的旧控制端、身份/内容不匹配、真实权限错误、损坏或缺失回执会明确报错，不盲重送未知请求。用户取消继续生效；恢复等待没有新增整个任务的总时间或次数上限。

进度与心跳事件不需要保存一份完整任务回执；偶发进度回传超时不终止业务执行，下次进度继续报告。任务租约续期和过期后等待原进程退出的规则保持不变。控制端 Runner 心跳在15秒内合并持久化，因此运维页面的最近心跳可能有这一量级延迟，不影响执行任务每30秒的续租事件。

## 状态读写与诊断

已提交的状态按文件 inode/大小/修改时间等签名缓存，任务状态检查只复制对应 Job；返回值与缓存隔离。发现文件替换会重新读取，不把外部旧副本冒充最新状态。空闲且没有待领取或过期任务时不重写整个文件；未改变内容的事务也不落盘。程序仍是单个控制面写入实例，不允许多个独立控制面同时修改同一状态文件；手工迁移或编辑仍须停稳备份。

`GET /health` 包含：

- `controlRequestProtocol=durable-control-v1`
- `stateReadPolicy=stat-cache-detached-v1`
- `pendingControlRequests`：当前等待完成的关键请求数。
- `stateTransaction.queueMs/transactionMs`：最近一次状态事务的排队与处理耗时，不是完整历史追踪。

如果界面长时间等待，先看服务健康、排队时间和本机日志；网络暂缓日志会说明正在核对回执。真实磁盘、配置、权限或过期租约问题仍需处理，不能把这些中断解释为已确认的业务原因。

## 保存、升级与回滚

`<AGENTOS_DATA_DIR>/agentos.json` 的 `controlReceipts` 保存编号、请求摘要、归属、文件摘要和时间。`<AGENTOS_DATA_DIR>/control-receipts/<请求编号>.json` 保存原响应，可能含任务取证信息，按私有运行数据保管、不入Git、不进入团队知识、不对飞书公开。目录与文件使用本机受限权限。

备份时停稳控制面和Runner，将状态文件与回执目录一起备份和恢复。不能只恢复索引或只删正文；缺失时系统拒绝重复执行。没有自动过期清理服务，不随意删除仍可能等待接续的回执。发生断电、文件丢失或损坏时先保留现场和原任务，不能用清空索引绕过检查。协议覆盖本机状态提交与响应恢复，不承诺跨进程崩溃后业务工具的任意副作用恰好一次；原有租约防重复执行规则仍须保留。

升级无新权限或依赖：更新源码后在没有在途任务/对话时备份并重启 Control Plane 与 Runner，核对 health 两项标记。旧红卡保留原证据，不自动修改为成功、不绕过新授权重跑历史PRD。

## 验证边界

自动回归覆盖真实HTTP响应丢失、慢于10秒的领取、环境准备和结果回传恢复、取消、身份/内容冲突、事务回滚、重启后读取回执及文件损坏；均使用合成数据，不查询真实PRD或发群测试消息。真实约41MB状态的隔离副本中，同一组心跳/空闲租约/任务读取从约8.7秒降到0.9秒，整文件写入18次降到3次；这不是所有机器或繁忙场景的固定性能承诺。Windows/Linux的实际部署、客户端效果与具体业务问题仍按各自环境验收。
